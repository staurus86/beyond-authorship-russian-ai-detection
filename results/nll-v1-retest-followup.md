# Процедура 3: проверка повторяемости показывала разрешение записи, а не недетерминизм

`nll-v1-manifest.json` содержит `max_abs_delta = 4.464e-07` по десяти документам, и по §5 спецификации это записано как расхождение с ожидаемым побитовым совпадением. Ожидание при этом выполнено — сравнение было построено неверно.

## Что сравнивалось на самом деле

Расчётный скрипт складывает результаты в CSV с округлением до шести знаков, а при повторной проверке берёт первое значение обратно из этой таблицы:

```python
first = float(next(r["nll"] for r in rows_out if r["document_id"] == row["document_id"]))
```

То есть округлённое число сравнивалось с полным. Отсюда и величина: у `deepseek_pro_b001_P1_r1` записано 2.747998, посчитано 2.7479984221131764, разница 4.221e-07 — ровно половина последнего разряда записи.

## Чистая проверка

Десять первых документов посчитаны дважды подряд, сравнивались полные значения float, 2026-07-28 после завершения прогона:

**Вывод: расчёт NLL на CPU с float32 детерминирован**, как и предполагала §5. В публикации величина 4.464e-07 подаётся как разрешение записи в CSV, а не как нестабильность расчёта.

**Что стоит поправить в коде перед следующим прогоном:** сравнивать полные значения, а не прочитанные из таблицы. Результаты процедуры 3 при этом не меняются — округление касается только записи, а контрасты считаются по полным числам, которые живут в памяти до конца прогона.
