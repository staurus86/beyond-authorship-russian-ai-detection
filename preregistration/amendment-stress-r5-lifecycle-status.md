# Дополнение к амендменту r5: статус жизненного цикла прогона

Дата регистрации: 2026-07-31, зона `Europe/Moscow`. Решение PI по итогам
конфликта, вскрытого синтетическими тестами перед прогоном r5.

Основной амендмент `amendment-stress-r5-t14-not-executable.md` **не изменяется**:
его хеш уже входит в манифест деривации `stress-p4-r5-manifest.json`, и правка
задним числом лишила бы закрытую деривацию воспроизводимости. То же относится к
манифестам ревизии r4.

## Проблема

Условие 7 шлюза завершения P1 требует, чтобы манифест предыдущей ревизии нёс
флаг `invalidated`. Формулировка появилась, когда прежний прогон всегда оказывался
негодным: r2 и r3 были инвалидированы за дефекты.

Ревизия r5 в эту схему не укладывается. Прогон r4 завершён штатно, его шлюз дал
`completed`, а P4 ревизии r5 получен деривацией именно из него — то есть r4
служит источником происхождения действующего результата. Пометить его
`invalidated` значило бы вывести действующий результат из негодного источника.

Оставить условие как есть тоже нельзя: без пометки шлюз блокирует прогон r5.

## Решение: два независимых статуса

Статус прогона разделяется на два поля.

`execution_status` — чем закончился сам прогон: `completed`, `incomplete`,
`failed`. Это свойство исполнения, оно не меняется никогда.

`lifecycle_status` — какое место прогон занимает в цепочке ревизий:

| Значение | Что означает | Может ли быть источником |
|---|---|---|
| `current` | действующая аналитическая ревизия | да |
| `superseded` | артефакт сохранён и пригоден как источник происхождения, но финальной ревизией не является | да, в пределах заявленной области |
| `invalidated` | результат вычислительно или содержательно непригоден | нет |

Разница между `superseded` и `invalidated` содержательная. Инвалидированный
прогон не может стоять выше по течению ни для чего. Заменённый — может, и область
его пригодности указывается явно.

Для P4 ревизии r4: `execution_status` — `completed`, `lifecycle_status` —
`superseded`, `reusable_scope` — десять преобразований без t14, `superseded_by` —
P4 ревизии r5.

## Как это записывается

Статус жизненного цикла хранится в отдельном неизменяемом sidecar-файле рядом с
манифестом, а не внутри него:

```
07-analysis/stress-p4-r4-lifecycle.json
07-analysis/stress-p1-r4-lifecycle.json
```

Sidecar содержит:

- `manifest` — имя манифеста, к которому относится запись;
- `manifest_sha256` — хеш этого манифеста на момент записи, неизменённого;
- `execution_status` и `lifecycle_status`;
- `reason` — почему статус изменился, со ссылкой на амендмент;
- `reusable_scope` — область, в которой артефакт остаётся пригодным;
- `superseded_by` и хеш манифеста-преемника, если он уже существует;
- отметки времени UTC и по Москве.

Сам манифест прогона не редактируется. Его хеш, записанный в чужих манифестах,
остаётся верным.

## Что проверяет условие 7 после правки

Прогон блокируется, если хотя бы одно не выполнено:

1. у предыдущей ревизии есть sidecar;
2. `manifest_sha256` в sidecar совпадает с фактическим хешем манифеста;
3. `lifecycle_status` — `superseded` либо `invalidated`;
4. у `superseded` заполнены `superseded_by`, `reason` и `reusable_scope`;
5. новый манифест не перезаписывает прежний.

Предыдущая ревизия со статусом `completed` и без sidecar запуск блокирует: это
означает, что действующая ревизия не объявлена заменённой, и две ревизии
претендуют на роль текущей одновременно.

## Проверка кода до прогона

`09-tools/test_stress_gates_synth.py`: **67 проверок, провалов нет**. Было 60;
семь добавлены на статус жизненного цикла — четыре обязательных по решению PI и
три сверх того, на неполные записи:

| Сценарий | Ожидание |
|---|---|
| корректный `superseded` со всеми полями | проходит |
| корректный `invalidated` | проходит |
| прежняя ревизия `completed` без sidecar | блокирует |
| sidecar с хешем, не совпадающим с манифестом | блокирует |
| `superseded` без `superseded_by` | блокирует |
| `superseded` без `reusable_scope` | блокирует |
| статус `current` | блокирует |

Каждый сценарий работает на временном манифесте во временном каталоге: тест не
читает и не трогает файлы ревизий.

Прежние 60 проверок пришлось поправить в одном месте: число ячеек в них было
записано числом 660 и разошлось бы с составом прогона. Теперь оно вычисляется как
`60 × len(TRANSFORMS)`, то есть меняется вместе с составом автоматически.

## Что не меняется

- Основной амендмент r5 и его хеш.
- Манифесты и журналы ревизии r4.
- Манифест деривации `stress-p4-r5-manifest.json` и его входные хеши.
- Состав преобразований, знаменатель 10, число ячеек 600.
- Пороги нестабильности по процедурам.
